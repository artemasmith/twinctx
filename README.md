# TwinCtx

TwinCtx — долговременная память для цифрового двойника человека. Руководитель, эксперт или автор собственной ИИ-системы может сохранять в ней решения, основания и рабочие правила. Когда агенту нужно действовать, он запрашивает применимые к задаче записи вместе с их источниками.

Например, в январе руководитель запускал пилот после трёх интервью. В феврале он поднял порог до пяти и записал причину. Для нового запуска агенту нужно февральское правило. Для разбора январского решения нужна прежняя версия. TwinCtx хранит обе записи и учитывает, когда каждая из них действовала.

## Попробовать на своём решении

Для примера нужны Python 3.11+ с SQLite FTS5 и терминал macOS или Linux. Команды создадут временное хранилище без сетевых сервисов и ключей API.

```sh
git clone https://github.com/artemasmith/twinctx.git
cd twinctx
python3 -m venv .venv
. .venv/bin/activate
python -m pip install .

export HARNESS_HOME="$(mktemp -d)"
export TWINCTX_STORE=sqlite TWINCTX_EMBED=none

first=$(twinctx remember 'Пилот запускаем после трёх интервью.' \
  --about launch --valid-from 2026-01-01)
twinctx remember 'Пилот запускаем после пяти интервью: так мы услышим и новых клиентов.' \
  --about launch --valid-from 2026-02-01 --supersedes "$first"
twinctx query 'Когда запускаем пилот?' --corpus memory --json
```

В `packed` будет правило про пять интервью, а в `manifest.items` — ссылка на запись из `memory/launch`. Связь между версиями задаёт автор записи через `--supersedes`. Чтобы получить правило на конкретную дату, в Python API передайте `as_of` в `AssembleRequest`.

Для постоянной работы выберите постоянный каталог `HARNESS_HOME`. Команда `twinctx export-memory decisions.jsonl` сохраняет факты вместе с историей версий. Команда `twinctx import-memory decisions.jsonl` восстанавливает их в выбранном хранилище. Чтобы дополнить память документами, укажите каталог Markdown-файлов в `VAULT_DIR` и выполните `twinctx index`.

## Что делает TwinCtx поверх хранилища

TwinCtx задаёт правила записи и замены фактов, отбирает сведения на указанную дату и собирает контекст в пределах бюджета агента. Вместе с текстом агент получает манифест с источниками. Само хранение и чтение выполняет адаптер `Store`. В поставке есть SQLite и PostgreSQL. Для подключения нового хранилища нужен адаптер, который сохраняет ту же семантику памяти.

Для интерактивной работы важна задержка от вопроса до готового контекста. Её стоит измерять на архиве владельца вместе с качеством выдачи: успел ли двойник вернуть действующее правило и указать его источник.

## Подключить агента

Установите MCP-адаптер в том же окружении и запустите его через MCP-клиент по stdio. В конфигурации клиента укажите полный путь к исполняемому файлу `.venv/bin/twinctx-mcp` и передайте те же значения `HARNESS_HOME`, `TWINCTX_STORE` и `TWINCTX_EMBED`.

```sh
python -m pip install '.[mcp]'
```

Агент может запросить контекст через `context_assemble`, прочитать конкретный источник через `context_read` и записать факт через `context_remember`. Из терминала память доступна через `twinctx remember`. Поиск поддерживает переходы по ссылкам между заметками и ограничение выборки по корпусу. Опциональные адаптеры устанавливаются отдельно через extras `embeddings`, `postgres` и `privacy`.

Индексатор также читает задачи из `$HARNESS_HOME/workspace/<проект>/.tasks/*.yaml` и журнал из `$HARNESS_HOME/journal/`. Интеграция с Hermes в этой поставке доступна через MCP.

## Семантический поиск проектных документов с QMD

`twinctx project-query` и MCP-инструмент `context_project_search(project, query)` ищут в Markdown выбранного проекта. Сначала TwinCtx проверяет свой индекс. Если поиск завершился с пустой выдачей и включён QMD, вопрос поступает в векторный индекс этого проекта. Если первичный поиск дал сбой, TwinCtx сообщает об этом.

Проект задаётся в начале Markdown-файла в каталоге `VAULT_DIR`. Пример содержимого `archive.md`:

```markdown
---
project: demo
---
# Хранение архива
Резервные копии хранятся сорок пять дней.
```

TwinCtx сверяет найденный путь и SHA-256 с исходным файлом и проверяет цепочку редакций. В новой версии документа можно указать `supersedes: archive.md`. Ответ содержит цитату и ссылку на действующую редакцию. Если QMD нашёл смысловое совпадение, а подходящую цитату выделить не удалось, инструмент возвращает ссылку на возможный источник. Неоднозначная цепочка редакций даёт ответ о неопределённости.

**Запуск на Linux-сервере.** Нужны Node.js 22+, npm, установленный TwinCtx и копия этого репозитория. Сборка и обслуживание QMD используют модель EmbedGemma на машине сервиса. При первой сборке QMD скачивает веса. Сервис слушает `127.0.0.1:26358`. Выполните из корня репозитория:

```sh
export HARNESS_HOME="$HOME/twinctx-data" VAULT_DIR="$HOME/vault"
export TWINCTX_STORE=sqlite TWINCTX_EMBED=none
npm ci --prefix deploy/qmd
python -m twinctx.qmd_refresh "$VAULT_DIR" "$HARNESS_HOME/qmd" deploy/qmd/server.mjs
node deploy/qmd/server.mjs serve "$HARNESS_HOME/qmd"
```

В другом терминале с теми же настройками хранилища проверьте готовность сервиса и выполните запрос:

```sh
curl -f http://127.0.0.1:26358/health
export TWINCTX_QMD_ENABLED=1
twinctx project-query demo 'Когда удаляют бэкапы?'
```

Для MCP передайте `TWINCTX_QMD_ENABLED=1` и `VAULT_DIR` в окружение процесса `twinctx-mcp`. После изменения документов повторите `twinctx index` и команду `qmd_refresh`. Обновление переключает QMD на новый индекс только после завершения сборки. Храните каталог индекса за пределами Vault. Зависимости QMD и веса модели распространяются на своих условиях. [QMD](https://github.com/tobi/qmd) · [EmbedGemma](https://huggingface.co/google/embeddinggemma-300m)
